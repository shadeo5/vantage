Technical Decision Record

Vantage

A photographer's scout that answers “what should I shoot near me right now?” — and the reasoning behind how it's built. This is the running log of the choices that shaped the app, why we made them, and what we deliberately deferred.

Project Vantage / StreetPhotoApp Updated Jul 11, 2026 Stage Slice 3 of 6 City Atlanta
01

The thesis

What the product actually is — the decisions that define the problem before any code.

Focus

Street-first, landscape later

Decision: Build and prove the street / street-portrait case first; add landscape later.

Why: Landscape is already solved — you can Google “best photo spots in a national park.” The hard, differentiated value is finding human activity and density to shoot, which is worst when you're not in a major city. Don't spend effort re-solving what a search engine does.

Data strategy

Auto-generate, don't hand-curate

Decision: Generate the “go shoot here” list from open data instead of manually curating spots.

Why: No existing spot database, and curation doesn't scale to every city. A throwaway proof-of-concept confirmed the generated Atlanta list was genuinely useful.

Identity

Keep the “Vantage” look, rebuild the brain

Decision: Reuse the existing dark, editorial Vantage design; replace its content signals from landscape (vistas, quiet) to street (activity, crowds).

Why: The design was already done and strong. For street, a busy scene is the goal — the opposite of the scenic-scout framing the mockup implied.

02

Data & architecture

How the “go shoot here” list is actually assembled and ranked.

Places

OpenStreetMap → walkable districts

Decision: Pull interesting POIs (markets, squares, pedestrian streets, arts venues, parks, public art) from OpenStreetMap via Overpass, then cluster them into districts (greedy, ~500m merge).

Why: Raw output listed a dozen individual statues near the Capitol. Photographers want an area to wander, not a pin per statue. Clustering turns 295 POIs into ~95 coherent districts.

Events

Filter by geography, never by name

Decision: Match events by venue latitude/longitude + radius, not by a city text field.

Why: Searching “Atlanta” returned a soccer club in Argentina named Atlanta. Location is a coordinate, not a string.

Coverage

Multi-source events + an editorial “tentpole” layer

Decision: Combine several event feeds, and hand-pin a small set of huge, known-months-ahead events.

Why: No single API is complete. The FIFA World Cup semifinal in Atlanta sells through FIFA (not Ticketmaster) and wasn't in the sports feed yet (knockout teams undecided). The editorial layer guarantees the biggest shoot in town never silently drops.

Light

Sun altitude drives the light curve

Decision: Compute golden/blue-hour and a per-30-min light-quality curve from the sun's altitude with SunCalc — no network.

Why: Light is pure astronomy; it's exact, free, and offline. Bar height ramps up to the golden-hour peaks and down through the harsh midday trough, rather than flat category blocks.

04

Frontend & build

Framework

Expo (React Native) + TypeScript

Decision: One codebase for iOS and Android, on Expo SDK 57.

Why: A single JavaScript/TypeScript codebase ships to both platforms and is the friendliest path for a non-native developer working with AI assistance.

Navigation

State-based screens for now

Decision: Switch screens with a simple state value; add a real navigation library only when the tab bar lands.

Why: The thinnest thing that makes tapping a card work — and it mirrors how the original mockup managed screens. Don't add infrastructure before it's needed.

Imagery

Photo-less cards, on purpose

Decision: Use tonal gradients on cards instead of stock photos, for now.

Why: No licensed imagery yet. Fake stock would misrepresent the product; honest placeholders read as intentional. Imagery is a real, open decision (see below).

Method

Vertical slices

Decision: Build in thin, end-to-end, phone-runnable slices — data → logic → UI — one at a time.

Why: Every slice is something you can open and use. We never sit on a broken half-built app.

05

Learnings & gotchas

Things that bit us — kept here so they don't bite twice.

Flickr → Pro
Flickr now requires a paid Pro subscription just for an API key. Dropped it — OpenStreetMap is free and better-aimed at street anyway.
Rate limits
Firing 60 parallel requests at a free API earned an instant HTTP 429. Fixed by querying smart (per-team endpoints), not brute-forcing every day.
Free-tier caps
TheSportsDB's free tier silently caps at ~5 results per endpoint — useless for real schedules. Switched to ESPN's free API, which returns complete seasons and is CORS-enabled for web.
Geo, not names
Text matching “Atlanta” pulled in an Argentine football club. Always filter by coordinates + radius.
SunCalc units
This SunCalc build returns sun altitude in degrees, not radians — converting again inflated values and flattened the light chart. Will matter again for the sun-compass.
Overpass 406/504
Overpass rejects a missing User-Agent (406) and times out under load (504). Fixed with a real UA header and mirror fallback.
Expo Go vs SDK
Store Expo Go is older than SDK 57, so phones show “needs update.” Testing on web preview for now; a dev build (or SDK downgrade) unlocks phones later.

07

Open questions

  • Area imagery. Where do photos come from — Wikimedia Commons (free, attribution), Mapbox thumbnails, or user-contributed? Licensing is a real product decision.
  • What each area should capture. The data model per spot — sample shots, subjects/genre, access, safety, energy — plus what truly signals a good street spot beyond POI density.
  • Live busyness. Real-time “is this street crowded right now” has no clean free source; scheduled events + POI density are today's proxies.
  • Weather-aware light. The light curve is pure sun geometry; Open-Meteo cloud cover should temper it so golden hour only lights up when the sky cooperates.
  • Accounts. Anonymous/local vs. real sign-up — needed once saving and routes sync across devices.
