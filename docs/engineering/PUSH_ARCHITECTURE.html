The Push Nudge

How the in-app nudge becomes a real notification — your phone buzzing "great evening to shoot" even with the app closed. The north star, and the last missing piece (N2).

Doc ADR — push / backend Status Design · pre-build Updated Jul 13, 2026
01

Why a backend at all

The nudge brain (lib/nudge.ts) runs inside the app today — so it only decides when the app is open. To push when the app is closed, the decision has to move to the cloud and run on a schedule. That's the whole reason for a backend.

App · your phone
register push token
save your gear
▶
Supabase · the cloud
daily cron fires
run the nudge brain

"…worth a look tonight"
The reuse win

The brain and copy are pure TypeScript with no UI. Supabase Edge Functions run Deno/TS — so the same nudge.ts + nudgeCopy.ts port to the server. The push reuses what we already built and tested.

03

Data model (minimal)

users(id, push_token, timezone, created_at)
gear_profiles(user_id, camera_id, lens_ids[])
nudge_log(user_id, spot_id, sent_at)   // dedupe + history

Start anonymous — a device id is enough to store a push token + gear and send a nudge. Real accounts (email/social) come later, only if we need cross-device sync.

05

Open questions

  • What local time to fire, and how do we handle each user's timezone?
  • Quiet hours / frequency cap — nudging every single night reads as spam. Skip low nights (N1 already can) and cap frequency?
  • Dedupe — don't headline the same spot two nights running (that's what nudge_log is for).
  • Auth — anonymous device id now; real accounts only when sync/discovery needs them.
  • Journal — keep the return-metric local, or sync it up so we can actually measure engagement across users?
