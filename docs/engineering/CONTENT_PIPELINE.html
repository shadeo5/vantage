Architecture · Engineering

Content at Scale

How a new place — Nashville, Chicago, Blue Ridge — goes from a name to a vetted, illustrated, served spot list. Mostly automatic, with one human gate where it matters, and a both/and data model: git for review, Postgres for serving.

Doc ADR — content pipeline (E1 · C1/C4) Status Proposed · D1 + D2 decided · D3 open Updated Jul 14, 2026
01

Why now — and the smell we already have

The app runs on 5 hand-authored Atlanta spots (lib/spots.ts). Adding a city by hand doesn't scale, and there's a concrete problem hiding in the code today:

The duplication

The spot list is already copied in two places — vantage/lib/spots.ts (the app) and supabase/functions/nudge/index.ts (the server that decides what to push), the latter with a literal // keep the two in sync comment. Two hand-synced copies of five spots is fine. Two hand-synced copies across four cities is not. Scaling content is the moment to collapse this to one source.

So this ADR answers two coupled questions: how does a city's spot list get produced automatically, and where does that content live so the app and the server read the same truth.

03

The both/and data model

Not file or database — both, each doing the job it's good at. Git reviews content; Postgres serves it; Storage holds the images.

  • Source of truth = git-committed per-city JSON. The human gate's output, reviewed in PRs — fits the human-in-the-loop and docs-with-every-commit workflow.
  • Serving = Postgres (Supabase, already live). An importer loads approved JSON into a spots table. Both the app and the Edge Function read from it → the §01 duplication dies.
  • Images = Supabase Storage, referenced by URL. You cannot bundle N cities × ~3 MB illustrations in the app binary.
  • App keeps a bundled Atlanta fallback for offline / instant first launch — stale-while-revalidate (E4 B3).
Why design the DB now, not later

(1) the duplication already exists; (2) images force remote storage at any scale, and metadata wants to live next to them; (3) it avoids doing the wire-in twice — an ad-hoc JSON shape read by the app, then re-done for Postgres later, means redoing both the app data layer and the edge function. Define the shape once. The backend is already stood up, so a spots table is a small extension, not new infrastructure.

04

The schema — small on purpose

Basically the existing Spot type + city_id + image_url. Two tables.

-- a place we cover (city, or a nature region like Blue Ridge)
create table cities (
  id            text primary key,   -- slug: 'nashville', 'blue-ridge'
  name          text not null,
  region        text,                -- 'TN', 'GA mountains'
  genre_profile jsonb not null,      -- weights that tune curation (§05)
  center_lat    double precision,
  center_lon    double precision,
  published     boolean default false
);

-- one shootable spot, matching the app's Spot type
create table spots (
  id          text primary key,
  city_id     text references cities(id),
  name        text, type text, genre text,
  window_type text,                  -- 'golden' | 'blue' | 'flat'
  reason      text, tagline text, why text,
  look        text[],                -- the 3 'what to look for' tips
  getting     text,
  lat         double precision, lon double precision,
  image_url   text,                  -- → Supabase Storage, not bundled
  published   boolean default false
);
What we're NOT adding yet

No PostGIS / geo-indexing. The app filters spots client-side; a flat "give me this city's spots" query is enough. Geo-indexing earns its keep only when "spots near me across cities" matters — which is real-GPS + precompute-and-serve (E4 B2), a later slice. Don't build it on spec.

05

Curation is the hard part

Stages 3–5 are mostly plumbing. Deciding which places make the list is the real open problem — and OSM alone won't fully answer it.

  • OSM Overpass (free, no key; already prototyped in scout.mjs) is the spatial backbone — it reliably finds viewpoints, parks, bridges, markets, historic districts with real coordinates.
  • What it misses is "where photographers actually go" — the mural alley, the overlook locals know. So blend in an LLM "local scout" pass that proposes named spots, then resolve each back to real OSM/Wikidata coordinates — a proposed place with no findable coords gets dropped automatically (kills hallucinations).
  • The human gate (stage 2) catches the rest. It's load-bearing, not a rubber stamp.

Your three examples prove the pipeline must be genre-adaptive, not city-shaped — Blue Ridge isn't a city at all. The genre_profile tunes the OSM queries and scoring:

BriefShapeCuration weights toward
ChicagoCityscape / street / architectureskyline vantage points, river bridges, L platforms, plazas
NashvilleStreet / music / muralshonky-tonk strips, mural walls, the pedestrian bridge, markets
Blue RidgeNature / landscape (a region)overlooks, waterfalls, trailheads, sunrise/sunset vistas

One pipeline, different weights — not three bespoke scripts.

06

Draft & image

Draft is largely done: generate.mjs takes {name, genre, lat, lon} → Claude with the Spot JSON schema and the voice guide baked in → why / look / getting / tagline / windowType. Validated as good on 8 unseen Atlanta spots (you approved them); it's never been run for real (API spend). The vetted list from stage 2 is its input — clean boundary.

Image scales the manual C2 step: one stylized illustration per spot from docs/design/ILLUSTRATION_STYLE.md + the spot's specifics. This holds the honesty line — art, not fake photos of a real place — and the output lands in Storage as image_url.

On "possibly an agent"

The built pipeline is a cheap one-shot structured call. An agent would web-research each place first (real, current detail) then draft and self-check against the voice + honesty rules — meaningfully better for places the model knows thinly (a specific Blue Ridge trail), but slower and costlier. Recommendation: start one-shot (proven), add a research-agent enrichment layer only where copy reads generic. Decision D2 below.

07

The payoff: one source, no more hand-sync

Once stage 5 lands, both readers point at Postgres and the §01 smell is gone for good:

  • App fetches a city pack (spots JSON + image URLs) from the DB, cached on-device (B3), with the bundled Atlanta pack as the offline/first-launch fallback.
  • Nudge Edge Function reads spots from the same table instead of its hand-copied SPOTS[] — so the server can nudge for any published city, and there's nothing left to keep in sync.
08

Build order

Prove the human-gated loop end-to-end on one city before investing in the scout, the agent, auto-imagery, or the backend swap.

  1. Curate → Vet, one city (Nashville), OSM-only. Productionize scout.mjs into "city brief → ranked candidates + a review view you approve." Emits vetted.nashville.json. No spend yet.
  2. Run the existing draft pipeline on the vetted list; eyeball the copy. This is the first real API spend — a few dollars — and the true quality test.
  3. Stand up the spots/cities tables + importer; load approved JSON. Point the Edge Function at the table → retire the duplication.
  4. App reads the city pack from the DB with the bundled fallback (B3 cache).
  5. Then, as volume grows: LLM-scout blend (better curation), auto-imagery, and precompute-and-serve (B2) when the 3rd/4th city makes it pay.
09

Decisions

  • D1 · Curation ambition. Decided: OSM-only for city #1. Curate candidates from OSM Overpass — reusing archive/poc/scout.mjs's query + scoring, retargeted from "near me now" to "rank a city's photo-worthy places" by genre_profile relevance, prominence, and district clustering — and let the human vet fill the local-knowledge gaps. Escalate to the OSM + LLM-scout blend when vetting shows the gate mostly adding spots OSM never surfaced rather than pruning a good list. OSM-only isn't the cheap option — it's the measurement: city #1's vetting is how we learn whether the scout is worth building.
  • D2 · Draft: agent or one-shot. Decided: one-shot default, agent as a targeted upgrade. The proven one-shot (generate.mjs) drafts every spot; a spot escalates to the research-agent pass (web-grounded, then self-checked against the voice + honesty guide) only when its vet-stage copy is vague or its specifics can't be trusted — typically thin-knowledge places (an obscure Blue Ridge overlook), not major-city landmarks. So the extra cost is spent only where it buys accuracy, and the trigger is the quality review, not an upfront choice. How often the agent is actually needed is a question city #1 answers.
  • D3 · Imagery route. Which image model / service generates the per-spot illustrations, and at what cost/size (the current ~3 MB assets need compression regardless)? Open.
